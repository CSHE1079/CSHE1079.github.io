一

系統架構

分成三區：Microsoft 雲端、院內防火牆、院內網路。對外只開一個入口（Teams 按鈕回傳），通知 API、操作後台、資料服務都只在內網。主程式不直接連資料庫，所有讀寫都經資料服務（SrvApi），每個動作一次完成、不會做一半。

從外部進來或內網呼叫 平台主動對外連線（不需開放入口） 把回覆送回原系統
  • 1員工在 Teams 收到通知卡片、按下按鈕。
  • 2Teams 把按鈕點擊送進來，平台先驗證確實來自 Microsoft。這是唯一對外入口。其他路徑除了 WAF 擋住，主程式內也再檢查一次：只接受設定檔列出的內網網段。
  • 3平台主動把卡片送到個人對話或頻道，並在有人回覆後更新原卡片。
  • 4用員工代碼推出公司帳號（csh{員工代碼}@csh.org.tw），查出對應的 Teams 帳號。頻道成員第一次按按鈕時則反過來：依 Microsoft 帳號識別碼（Object ID）查出公司帳號，再對到在職員工。
  • 5介接系統帶金鑰呼叫通知 API：建立（可指定發送時間）、取消尚未開始的通知、查詢結果；有附件時先以 POST /attachments 上傳取得附件編號，建立通知時帶 attachmentIds[]。
  • 6三種事件（通知回覆、發送結果、通知未發送）附防偽簽章送回介接系統；暫時送不到會依間隔自動重送。
  • 7平台管理者維護設定，也能在後台做介接系統能做的事：發通知、排程、修改或取消、查看回覆。白名單與後台人數上限放主程式設定檔，修改需重新部署。
  • 8主程式透過內網呼叫資料服務，呼叫要帶金鑰；金鑰放在密鑰存放處，不寫在設定檔。
  • 9防重複、搶第一位回覆等判斷，都在資料服務的單一交易與資料庫規則內完成；認領期限與到期判斷也一律以資料服務的時間計算，主程式不自己算。
  • 10資料服務經 Microsoft Graph 把附件上傳到平台專用的 SharePoint 文件庫，開始發送時依收件者授與檢視權限。App 只申請 Sites.Selected，只授權這一個網站（角色 fullcontrol）。
對外只開一扇門只有 Teams 的按鈕回傳能從外部進來；通知 API、後台、資料服務都只在內網。防火牆設定錯誤時，主程式內的內網網段檢查仍會擋下。
資料統一由資料服務處理主程式不直接連資料庫，與院內其他系統（例如文件辨識系統）的分層方式相同，方便維運與稽核。
資料放在院內標準資料庫使用院內建表格式，建表與結構異動由 DBA 執行。員工與單位資料直接讀取院內主檔，不另外複製。附件檔案本體存在平台專用 SharePoint，資料庫只存檔名、大小等資訊。
二

一則通知的旅程

以「簽核系統請主管核准一張單」為例，從建立到回覆送回共六步。每一步下方標示寫入的資料表（詳見第四、五節）。

建立

介接系統指定對象、標題、內容與回覆選項（有附件時先上傳、再帶入附件編號），呼叫通知 API。平台檢查是否在授權範圍內、選項格式是否正確、附件是否為自己上傳；重送同一請求不會建第二則（後台連點「送出」或瀏覽器重送表單也一樣）。

簽核系統：通知王主任「請核准請假單」
TeamsNotification・TeamsDelivery・TeamsAttachment

等待排程

可以立即發，也可在呼叫時帶入發送時間。開始前介接系統可用 API 取消、平台管理者可在後台修改或取消；開始後鎖定。

選擇立即發送
TeamsNotification

找人並發送

開始時重新檢查指定員工是否在職，排程期間離職者記為失敗「找不到員工」，其他人照常；超過人數上限或頻道已停用則整則不發送，並送「通知未發送」事件回介接系統。用員工代碼找到 Teams 帳號；有附件時先授與檢視權限，再把卡片送到個人對話或頻道；每位收件者分別記錄成功或失敗。

王主任的 Teams 跳出卡片
TeamsNotification・TeamsEmployee・TeamsDelivery

員工回覆

員工按卡片上的按鈕。平台記下誰、在哪個單位、選了什麼、何時。頻道成員第一次按、查不到身分時，即時向 Microsoft 反查並記住；反查失敗只提示本人「暫時無法確認身分，請稍後再試」。

王主任按「核准」
TeamsReply・TeamsDelivery・TeamsEmployee

更新卡片

卡片改成「已回覆」，其他裝置或頻道成員也看到最新狀態。多次失敗則放棄，後台顯示「卡片更新失敗」。

卡片顯示「您已於 10月20日 09:30 回覆：核准」
TeamsDelivery

回送原系統

平台把回覆送回簽核系統，附上防偽簽章；對方暫時收不到會自動重送。

簽核系統收到 APPROVE，自動結案
TeamsReply・TeamsDelivery
三

支援的使用情境

延續先前討論的功能情境，用語由「公告」改為「通知」。

情境 員工看到什麼 平台怎麼保證
私人通知 在自己與 App 的個人對話收到卡片，只有本人看得到；可開啟文件連結與附件。 每位收件者各自記錄送達結果，一人失敗不影響其他人。
私人通知回覆 按一次就完成。若在電腦按過，手機上的舊卡片再按會提示「已回覆過」。 每人只算一次；連點或網路重送都回傳原本的結果，不會重複計算。
頻道通知・單一回覆 單位頻道出現一張卡片，第一位按的人代表單位回覆，卡片對所有人關閉並顯示「已由 王OO（資訊室）回覆」。 兩人同時按，由資料庫決定唯一一位；發到多個頻道時各頻道各自計算。
頻道通知・每人一次 卡片保持開放並顯示「已有 N 人回覆」；自己按下時看到「您已回覆」，不會在頻道裡洗版。 每人只算一次，人數自動累加。
附件 卡片上每個附件一顆「開啟附件：檔名」，第一張圖片另附縮圖；在 Teams 內可直接預覽，手機與院外以 M365 登入開啟。 檔案存在平台專用 SharePoint；開始發送時才依收件者授與檢視權限，授權失敗則該對象不發卡片並標示失敗。
排程發送 指定時間自動送達。介接系統呼叫時帶入發送時間即可，不必自己等時間到再呼叫。 開始前可取消（API 或後台）、可修改（後台），開始後鎖定；服務中斷恢復後立即補發。「全部在職員工」在發送當下才決定名單；指定員工在發送當下重新檢查在職，已離職者標示「找不到員工」。
員工自己打字 App 回覆固定說明：「請用卡片選項回覆，其他問題請洽〔單位／分機〕」。 打字內容不保存、不轉給任何人。
查看回覆 平台管理者在後台看到每位回覆者與其當時的工作單位，可依選項篩選。 回覆當下的單位會被記住，之後人事調動不會改寫歷史。
四

資料怎麼存

新增 6 張資料表（由 18 張精簡為 5 張，2026-10-22 為附件新增 1 張，共 6 張），全部放在 HealthCare 資料庫。主線只有三層：一則通知 → 發給誰 → 誰回了什麼；另有平台設定、員工 Teams 身分與附件各一張。

通知一則通知發給多個對象 →投遞紀錄每個對象可收到回覆 →回覆紀錄

平台設定TeamsSetting

平台管理者在後台維護的設定：介接系統、可發佈頻道。

總量只有數十筆。

像「規則手冊」：誰能發、能發到哪。

通知TeamsNotification

每次發送一筆：誰建立的、標題內容、發文單位、回覆選項、排程時間、目前狀態；整則未發送時記錄原因並通知原系統。

回覆選項由介接系統每次帶入，隨通知保存、不再變動。

像「發文單」：這次要發什麼。

投遞紀錄TeamsDelivery

每位收件員工或每個頻道一筆：有沒有送到、失敗原因、卡片在 Teams 上的位置、已有幾人回覆。

也記錄要不要更新卡片、結果是否已通知原系統。

像「掛號追蹤單」：每一封寄到了沒。

回覆紀錄TeamsReply

每次有效回覆一筆：誰回的、選了什麼、補充文字、當時的工作單位、回覆時間。

也記錄是否已送回原系統。

像「回條」：誰回了什麼。

員工 Teams 身分TeamsEmployee

每位員工一筆：員工編號對應到哪個 Teams 帳號，以及與 App 的個人對話位置。

不存對話內容。

像「通訊錄」：這位員工在 Teams 的地址。

附件TeamsAttachment

每個上傳的檔案一筆：檔名、大小、類型、在 SharePoint 的位置、圖片縮圖，以及屬於哪則通知。

檔案本體存在平台專用 SharePoint 文件庫，資料庫只存這些資訊。

像「附件清單」：這則通知夾了哪些檔案、放在哪裡。

表與表的關係

外鍵：資料庫強制關聯（箭頭指向被參照的表） 用代碼或編號參照，不建外鍵（不影響院內既有主檔）
五

資料表明細

每張表說明：一列代表什麼、什麼時候寫入、有哪些欄位、靠哪些規則防錯。型別與長度為草案，實際以 DBA 審過的建表檔為準。

共通規範（院內建表格式）
  • 主鍵欄位 <名稱>No，自動編號（比照 EmpNo、DepartNo）。
  • 索引命名：主鍵 <表名>Key0，其他索引依序 Key1、Key2…（比照 Employee.sql）。
  • 會給外部看到的識別碼另存 GUID，不讓外人猜到流水號。
  • 時間一律存台灣時間；「還沒發生」存 2999/12/31。認領期限與到期判斷一律由資料服務以自己的時間計算，主程式不自己算。
  • 交易類資料表都有 CreateUser・CreateTime・UpdateUser・UpdateTime；設定類（平台設定）只有 UpdateUser・UpdateTime。後台操作填平台管理者的員工編號；系統自動處理填 0，來源介接系統記在通知上。
  • 以資料庫權限保護，不另外加密；介接系統金鑰只存無法還原的雜湊。

什麼時候寫入
介接系統或平台管理者建立時新增；開始發送、完成、取消時更新狀態。開始發送後內容不再改變。開始時若超過人數上限或頻道已停用，整則不發送、記錄 FailReason；由介接系統建立的同時設為待送「通知未發送」事件。
事件共三種

回覆選項為什麼存在通知上
選項由介接系統每次帶入（1–5 個，可加「其他」），平台檢查格式後存在這則通知上。產生卡片、更新卡片、檢查員工按下的回傳值都以它為準；建立後不再變動。

Key2 不重複 (SystemCode, RequestId)，介接系統與後台共用，套用所有通知
Key3 查詢用 (Status, ScheduledTime)：找出到期的排程
Key4 查詢用 (HookStatus, HookNextTime)：找出待送的「通知未發送」事件

ReplyOptions 的 JSON 格式

介接系統建立通知時帶 options、allowOther；平台檢查通過後，原樣存進 TeamsNotification.ReplyOptions。replyMode 另存 ReplyMode 欄位，不在這個 JSON 裡。

欄位 型別 規則
options 陣列 0–5 個，依陣列順序顯示成按鈕；不帶或空陣列＝純通知
options[].label 字串 必填。員工看到的按鈕文字；1–40 字、不可只有空白；以純文字顯示
options[].value 字串 必填。送回介接系統的回傳值；1–50 字；同一則內不可重複；不可使用保留值 OTHER
allowOther 布林 選填，預設 false。true 時卡片多一顆「其他」，回傳值固定 OTHER，員工須輸入 1–500 字；至少要有 1 個 options
replyMode 字串 不在 ReplyOptions。只用於頻道通知且有選項時必填：SingleReply／PerPerson；私人通知不帶 
-- ① API 請求（節錄）：私人通知・核准／退回＋其他
{
  "requestId": "SIGN-20261021-0001",
  "empNos": [1234],
  "title": "請核准請假單",
  "options": [
    { "label": "核准", "value": "APPROVE" },
    { "label": "退回", "value": "REJECT" }
  ],
  "allowOther": true
}

-- ② 存入 TeamsNotification.ReplyOptions
{"allowOther":true,"options":[{"label":"核准","value":"APPROVE"},{"label":"退回","value":"REJECT"}]}

-- ③ 頻道通知・單一回覆（replyMode 存 ReplyMode=1）
{"channelCodes":["IT-NOTICE"],"replyMode":"SingleReply",
 "options":[{"label":"已處理","value":"DONE"}]}

-- ④ 純通知：不帶 options，ReplyOptions 存
{"allowOther":false,"options":[]}

-- ✗ 會被拒絕：超過 5 個、value 重複、value 用 OTHER、label 空白、
--   頻道有選項卻沒帶 replyMode、allowOther=true 但沒有 options

附件的決定（2026-10-22）

採平台代管、存於 SharePoint（ADR 0007），推翻「平台不儲存文件、只提供文件連結」的定義。

項目 決定
API 分兩步：先 POST /attachments（multipart，單一檔案）取得 attachmentId；建立通知時帶 attachmentIds[]。建立通知仍是一般 JSON，requestId 冪等不受影響；大檔不拖慢建立通知的交易。
儲存 資料服務經 Microsoft Graph 上傳到平台專用的 SharePoint 文件庫。App 註冊只申請 Sites.Selected，只授權這一個網站，網站角色為 fullcontrol（管理檔案共用權限需要，write 不夠）。資料庫只存中繼資料。
檢查 副檔名與 MIME 白名單（例如 pdf、jpg、png、docx）；單檔大小、每則通知總大小、檔案數上限（平台設定，預設值待定）；掃毒交由 SharePoint 內建防護；介接系統只能引用自己上傳、尚未附加到其他通知的附件。
授權 開始發送時依收件者授與檢視權限：私人通知授權給收件員工；頻道通知授權給該團隊成員或使用「組織內可檢視」連結；「全部在職員工」改用組織內可檢視連結（逐人授權會產生數千筆權限）。授權失敗則該對象不發卡片並標示失敗。
卡片 依序：「通知」標籤、發文單位、標題、本文、圖片縮圖（選配）、「開啟文件」（選配，即文件連結）、每個附件一顆「開啟附件：檔名」（連到 SharePoint；Teams 可直接預覽，手機與院外以 M365 登入開啟）、選項按鈕。縮圖只為第一張圖片產生：PNG／JPEG、≤ 1024×1024、≤ 1 MB，以 Base64 內嵌。
病人資料 通知內容（標題、本文、選項、附件）可否含病人資料、可否存放在 M365，由介接系統依院內病安與資安規範自行負責，平台不檢查。
保存期限 先不設限，不做到期刪除。

2026-10-27 決定

補齊頻道回覆者身分、整則未發送、卡片更新放棄與內網防護等細節（ADR 0008、0009）。

項目 決定
頻道回覆者身分 點擊時先以 Object ID 查 TeamsEmployee，查不到由主程式以 Graph 取得公司帳號（須精確等於 csh{員工代碼}@csh.org.tw），資料服務對到在職員工後寫入；Graph 失敗只回應點擊者「暫時無法確認身分，請稍後再試」（ADR 0009）。
再到職 再到職會取得新員工編號與新帳號，Object ID 不同不衝突；若仍遇到同一 Object ID 對到兩個員工編號，沿用「身分關聯衝突」禁送。
頻道 serviceUrl 存在 TeamsSetting 可發佈頻道那一列的 Content，新增時預先帶入院內租戶的值（主程式設定檔），「頻道測試核准」時驗證。
整則未發送 TeamsNotification 記錄失敗原因並送交第三種事件「通知未發送」（事件編號＝NotificationId），後台建立的通知仍不送（ADR 0008）。
卡片更新放棄 TeamsDelivery 加 CardStatus；429、503、逾時最多重試 5 次、不可重試的錯誤立即放棄，有新回覆時重新計次，後台顯示「卡片更新失敗」。
後台白名單與上限 平台管理者白名單與後台人數上限都放主程式設定檔，修改需重新部署。
後台防重複 後台表單開啟時產生一次性請求編號，與通知 API 共用 (SystemCode, RequestId) 不重複索引，套用所有通知。
排程期間離職 開始發送時重新檢查指定員工是否在職，已離職者記為失敗「找不到員工」，其他人照常發送。
時間判斷 所有認領期限與到期判斷都在資料服務以它的時間計算，主程式不自己算。
內網防護 主程式除 Bot 訊息端點外，其他路徑只接受設定檔列出的內網網段，與 WAF 並存。
